# Agent Gateway 项目简历与技术难点案例（确认稿）

> 本文基于当前仓库实现和开发记录整理，供简历项目经历使用。未在本项目实现的知识库切片、向量检索、Rerank、TTS 声音复刻和 RTC 弱网优化不列为项目成果；性能数字也不作无测量依据的承诺。

## 一、简历项目经历

### Agent Gateway｜多项目 AI 能力网关

**2025.03—至今**

面向多个 Agent 应用建设统一 AI 能力网关，提供项目隔离、成员权限、API Key、LLM/ASR 接入、额度和用量管理、项目上下文 API、操作与技术日志，以及 Docker Compose 部署能力。

**技术栈：** Python、FastAPI、SQLAlchemy 2、PostgreSQL、Alembic、httpx、WebSocket、React、TypeScript、Vite、Docker Compose、pytest、Ruff、mypy。

**技术要点：**

1. **设计多项目权限和凭据隔离。** 实现 owner/editor/viewer 项目角色及项目级 API Key；Key 只归属创建成员，成员降为 viewer 或被移出项目时自动撤销其 Key。数据库以 HMAC 摘要校验、加密密文支持授权查看，服务日志可追溯到成员、Key 和 Trace ID。
2. **建设 OpenAI 兼容 LLM 代理链路。** 支持 Chat Completions JSON 与 SSE 流式响应；通过模型路由前缀选择上游连接组，按优先级故障切换，并透传常用采样、工具调用及扩展参数。额度按用户总额和项目分配双重校验，采用预留、调用后结算和并发保护，避免并发请求突破额度。
3. **接入火山豆包 Seed ASR 2.0。** 管理员在网关维护上游密钥、Resource ID 和文件/实时端点；调用方使用网关 API Key 与公开模型名，无需接触厂商凭据。文件转写提供 OpenAI Audio Transcriptions 风格接口；实时识别采用 WebSocket 双向流，使 PCM 音频块上传期间即可接收 partial/final 事件，不必等整段录音上传完再识别。网关把调用方统一协议转换为火山专有 WebSocket 鉴权和二进制帧，并区分文件转写与实时流的上游 URL 和帧协议。
4. **为 ASR 建立独立秒额度。** 按音频时长预留并结算用户级及项目级额度，与 LLM token 额度分离；在成功、拒绝、上游失败和客户端断开等路径处理额度释放或结算，并将请求状态关联到统一请求/Trace ID。
5. **排查并修复 ASR 上游帧协议问题。** 结合 Trace 区分 WebSocket 握手成功与上游解码失败，定位空结束帧压缩标记与载荷不一致导致的 `ungzip payload: EOF`，修正帧编码并增加回归测试；同时识别上游无音频包超时的会话与计费取舍，不把持续发送静音误当作无成本保活。
6. **实现项目隔离的上下文数据服务。** 提供提示词模板、会话短期记忆、长期记忆和用户画像 API；运行时项目范围由 API Key 确定。短期记忆支持消息顺序和 TTL，资源更新采用版本检查避免覆盖并发修改；日志不保存模板、记忆或画像正文。
7. **统一操作日志和诊断追踪。** 将服务调用与项目管理事件纳入可筛选、分页的操作日志；管理员技术日志记录认证、额度、路由和上游诊断，两类日志通过 Trace ID 关联，同时避免记录提示词、回复、音频及密钥。
8. **完成可部署工程交付。** 提供 Docker Compose、后端镜像、前端静态资源导出和迁移部署脚本；项目不内置 Nginx，由服务器现有 Nginx 负责静态托管和反向代理。自动化验证覆盖后端单元/集成测试、OpenAPI 契约，以及前端类型检查、Lint 和构建。

## 二、重点难点案例集

以下案例按开发中实际遇到的设计和排查问题整理。面试时可选与目标岗位最相关的案例深入讲，不需要逐条背诵。

### 案例 1：项目隔离、成员权限与个人 API Key 的生命周期

**问题背景：** 网关同时服务多个项目；同一个项目有 owner、editor、viewer，且管理员的全局审阅权限也不能变成项目写权限。最初“项目有一把共享 Key”无法回答具体由哪个成员发起调用，也不能满足成员离开后立即废弃其凭据。

**难点：** 认证和授权是两件事：Key 要解析项目与成员身份，实际访问还要检查项目状态、服务订阅和成员角色。Key 又必须在创建者授权下可再次查看，但不能以明文存储；成员角色或关系变化还要同步处理凭据。

**处理方案：** 每把项目 Key 归属创建它的 owner/editor。数据库保存用于校验的 HMAC 摘要和用于授权读回的加密密文；列表查询只返回当前成员自己的 Key。成员被降为 viewer 或移出项目时，在同一事务中撤销其有效 Key。服务调用日志保存 Key ID、成员 ID 和用户名。公开项目/管理员 review 只授予只读能力，不提升写权限。

**面试重点：** 解释为何 API Key 既需要不可逆摘要又需要密文：摘要用于安全验证，密文用于已授权的管理页面显示完整 Key，两者目的不同；再说明角色变更与 Key 撤销的事务边界。

### 案例 2：OpenAI 兼容代理里的模型路由、上游池和参数透传

**问题背景：** 调用方希望沿用 OpenAI SDK，只改 `base_url` 和项目 Key；管理员则要维护不同供应商、连接和密钥，也希望模型升级时不必为每个模型写一条硬编码映射。

**难点：** 公共模型标识与供应商原生模型名、上游连接选择是不同概念。若把厂商逻辑散落在接口路由中，每增加供应商或路由规则都会影响业务层；若只做静态模型映射，又增加管理维护成本。

**处理方案：** 采用 OpenAI 风格 Chat Completions 契约。普通模型名按规则透传到默认连接池；`prefix/model` 按前缀选择对应连接组，并去掉前缀后把模型名交给上游。连接组按优先级尝试，在可重试的连接或上游失败时切换。尽量透传标准参数、工具调用和兼容扩展字段；后台以 Base URL 与 API Key 身份去重，避免相同凭据被配置到不同组后重复路由。

**面试重点：** 区分“API 协议兼容”和“模型能力完全一致”。代理可以统一请求/响应形状，但上游对参数、工具和流式行为的支持仍需校验；已向调用方输出流内容后不能透明切到另一个上游，否则会拼接两次不同生成结果。

### 案例 3：流式代理中的额度预留、结算和取消清理

**问题背景：** LLM 请求开始时还不知道真实输入/输出 token 数；流式响应可能在生成中断开，客户端也可能主动取消。若只在成功响应后扣额度，会有并发超额；若开始时扣最大值，则失败或短回答会多扣。

**处理方案：** 调用前按 prompt 估算和输出上限预留额度，同时校验用户跨项目总上限与当前项目分配额；成功后依据上游 usage 结算实际用量并释放多余预留。错误、取消或上游断开路径清理未使用预留；已有上游用量或已经输出的部分内容按定义计入中断用量。数据库事务/行锁保护并发预留，服务日志记录预留、上游和结算阶段。

**面试重点：** 这是一个“额度账本状态机”问题，不只是一次 `UPDATE`。需要能说明预留、成功结算、失败释放和客户端取消分别如何避免额度泄漏或双重扣减。ASR 采用同样生命周期思路，但以音频秒数计量。进程在请求中途崩溃后的预留回收需要独立的过期预留对账机制；当前实现重点覆盖请求正常收尾、异常和取消路径，面试时不要声称已经实现崩溃恢复对账。

### 案例 4：为什么实时 ASR 使用 WebSocket 流

**业务需求：** RTC Agent 持续采集麦克风音频；希望用户说话时就收到不断变化的 partial，并在静音判停后尽快收到该句 final，同时保持会话连接接收下一句。

**为什么选择 WebSocket：**

- 音频输入和识别事件需要同时双向传输：客户端连续上传二进制 PCM，网关在同一连接上异步推送 partial、final、error 和完成事件。WebSocket 提供持久的全双工通道，事件边界清楚。
- HTTP 文件转写的请求模型是“先提供完整音频文件，再得到一次转写响应”，适合录音文件和批处理，不符合实时麦克风边录边识别的交互。
- 常见 SSE 是服务端到客户端的单向事件流；若用它，还需要另一条 HTTP 请求承载连续音频，并额外协调会话 ID、排序、结束和错误处理。也可以另行设计 HTTP/2 双向流，但那会形成一套不同于当前标准文件转写接口的客户端协议。WebSocket 将一条实时会话的上行音频与下行识别事件放在同一连接管理。
- WebSocket 本身不保证识别质量、端到端延迟或网络可靠性；这些仍由音频帧大小、上游服务、客户端网络和生命周期管理共同决定。本项目没有实测对比数据，不宣称比 HTTP 低多少延迟。

**协议设计：** 客户端先发 JSON `start`（模型和音频格式），随后发 16 kHz、单声道、16-bit little-endian 裸 PCM 二进制帧；静音判停由上游产生语句 final，`{"type":"end"}` 只表示整条输入流结束。partial 仅用于界面更新，不应该启动 LLM；final 是调用方提交用户轮次的依据。

**面试重点：** 强调“为什么选传输协议”由交互方向和生命周期决定，而不是因为 WebSocket 一定更快。文件上传与实时流是两种调用模式，HTTP Transcriptions 和 WS streaming 可同时存在，不能互相替代。

### 案例 5：ASR 首期为什么只接火山，不宣称通用适配

**问题背景：** 用户希望调用方只配置网关 URL 和 model；火山豆包实时 ASR 实际还需要 Resource ID、厂商鉴权头、专有 WebSocket 地址和二进制帧协议。不同平台不一定使用相同的模型字段、资源标识或流式协议。

**设计取舍：** 首期只实现火山适配器，是为了先把一条真实链路端到端跑通：管理员配置火山 Key、Resource ID 和文件/实时 URL；调用方发送网关项目 Key 与公开 model；网关在内部解析路由并转换厂商请求/响应。公开 model 和火山 Resource ID 分开，避免把厂商专有资源字段泄漏到业务调用配置。

**为何不是“支持任意 ASR 平台”：** 文件转写可能能统一到 OpenAI 风格 multipart 语义，但实时识别的 WebSocket 握手、消息帧、分句标记、结束语义和鉴权方式存在厂商差异。只把 URL 做成可编辑字段并不能实现协议兼容。当前只接入火山，其他 Provider 暂未配置或实现；未来接新厂商时应新增 Provider Adapter 和协议映射，并用同一网关事件契约验证，而不是让调用方直接感知其原生协议。

**面试重点：** 说明首期收敛范围是工程风险控制，不代表 ASR 网关天然厂商无关。抽象稳定的是调用方协议、鉴权、额度、日志和错误事件；厂商协议转换仍是各自适配器的职责。不要把“留有扩展点”说成“已支持多个平台”。

### 案例 6：实时 ASR final 重复和累计文本

**问题背景：** 调用方收到 `transcript.final` 后会把识别文本作为用户消息提交给 Agent。若网关把上游重复快照再次转成 final，或者把整段累计文本当成当前语句，Agent 就可能重复记录前文并重复触发 LLM。仅按文本内容去重也不可靠，因为用户可能确实再次说出相同句子。

**排查与根因：** 最初提供的一条 Trace 只有两个 partial，随后客户端断开，没有 final 事件正文，因此这条 Trace 本身不能证明 final 在运行时重复。进一步从上游响应结构和转发代码检查发现：火山后续快照可能继续携带已确认语句；逐帧遍历 `utterances` 并无条件转发 `definite` 语句，会让同一段历史在多个上游快照中被重复发送。另一个风险是把 `result.text` 这种连接累计文本直接视作一条新 final。问题在于事件身份和语句范围没有被显式建模，而不是调用方仅仅缺少文本去重；通过 tracker 单元测试验证了这类重复投递路径。

**实现方案：**

- 使用上游语句起始时间和说话人标识构造当前网关会话内稳定的 `utterance_id`，同一语句在重复快照中得到相同 ID；后续再次说出相同文本但起始时间不同，会得到新 ID。
- 在会话级 tracker 中记录已完成语句 ID，重复 final 不再下发；partial 只作为当前语句状态更新，不被误当作 Agent 的用户轮次。
- 对包含 `utterances` 的结果逐句提取，只发送当前语句文本；兼容缺少分句信息的累计文本响应时，剥离已确认前缀，避免把之前文本重新包装成 final。
- 保持 WebSocket 会话生命周期与语句边界分离：静音判停完成一句时即可发 final，连接继续接收下一句；只有调用方发送 `end` 才结束整条流并进行最终完成处理。

**验证方式：** 为 tracker 增加针对累计快照、重复 final、累计全文增量、相同文本后续重说及连接未结束时语句 final 的单元测试；ASR 模块测试、Ruff 和 mypy 检查通过。实时接口文档同时定义事件格式、`utterance_id` 语义、静音判停、`end` 和错误行为。

**结果与边界：** 网关不会再把已确认的历史语句重复转换为新的 final，调用方可以依 `utterance_id` 识别同一语句的重复投递。可靠地区分相同文本的再次发言依赖上游提供稳定的语句时间信息；若没有 `start_time`，兼容路径只能使用列表位置，无法对所有上游改写场景作同等保证。这里不声称具体延迟或准确率提升，因为项目没有记录这些量化指标。

### 案例 7：ASR 音频文件和裸 PCM 流不能混为一谈

**问题背景：** 调试中出现过将 PCM 文件提交给文件转写端点、将带时长元数据要求的格式当作原始 PCM，或因 M4A/ffmpeg 依赖而误以为实时 ASR 也必须走文件解码的情况。

**技术原因与处理：** 当前 HTTP 文件转写接受 WAV/MP3/OGG/M4A 等有容器或编码信息的文件，网关从文件元数据或解码结果估算时长；裸 PCM 只有采样字节，没有文件头，无法单靠文件内容判断采样率、声道、采样宽度或总时长，因此它不属于当前 HTTP 文件端点支持的格式。实时 WS 要求调用方明确按协议提供固定格式 PCM，并由网关从字节数和采样参数计算音频时长用于额度预留。火山的文件转写与实时流还分别配置各自上游 URL（如 `bigmodel_nostream` 与 `bigmodel_async`），请求载荷和协议生命周期不同，不能把 WebSocket 流地址当作文件端点使用。

**面试重点：** 解释容器格式、编码格式、采样参数和传输协议是不同层次；`.pcm` 扩展名本身不携带时长，也不能据此保证音频是 16 kHz mono s16le。实时接口若要兼容其他 PCM 参数，必须明确让客户端传参或由网关转码，并评估计费与资源成本。

### 案例 8：操作日志、技术日志与隐私边界

**问题背景：** 用户需要看到项目内所有成员的操作和调用，管理员需要排查上游细节；两种视图的可见范围和信息粒度不同。若只做一种日志，要么用户看不到项目操作，要么把技术诊断和敏感字段暴露给普通成员。

**处理方案：** 数据库操作日志按项目隔离，项目成员（含 viewer）只能查有权访问项目的事件；管理员可全局筛选。管理员技术日志记录认证、额度、路由和上游阶段。两者共享 Trace ID 以关联一次请求，但技术诊断接口保持管理员专用。用量字段放在服务专属计量表，避免把 LLM token 列伪装成所有服务共有字段；提示词、模型回复、音频、API Key 和上游密钥不写入普通日志。

**面试重点：** 讲清楚“可关联”和“可见同一份数据”不同：Trace ID 是关联索引，不意味着所有人都能访问技术日志。日志模型要兼顾审计、诊断、权限和数据最小化。

### 案例 9：项目上下文里的短期记忆、长期记忆和用户画像

**问题背景：** 控制台最初容易把长期记忆和用户画像看成相同的数据。二者都能跨会话保存内容，但业务含义、数据结构和更新方式不同；短期会话历史又需要按消息顺序读取。

**处理方案：** 短期记忆保存 session 下有序的 role/content 消息，可按 TTL 过期；长期记忆保存可检索的文本条目及标签/元数据；用户画像保存项目定义的 JSON 状态对象。运行时只由项目 API Key 确定 project_id，所有资源查询首先按 project_id 限定。可变资源通过 expected version 检查并发更新，冲突返回 409，避免覆盖他人编辑。

**面试重点：** 不要按“都是记忆”统一成一个无边界 JSON blob；数据模型应反映生命周期和查询方式。项目上下文是数据访问服务，不等于模型推理服务，因此不扣 LLM token 额度。

### 案例 10：生产路径、前端静态托管与本地开发配置

**问题背景：** 服务器计划使用现有 Nginx 统一管理多个应用；本地开发又不使用反向代理。若把 `/gateway/`、前端资源路径、控制台 API 和 Agent API 混成同一条前缀，容易与服务器上的其他 `/api/` 服务冲突，也会让本地开发配置复杂。

**处理方案：** 网关容器只提供应用服务和前端构建产物，不内置 Nginx。由部署文档指导服务器管理员将 `/gateway/` 页面、`/gateway/api/` 控制台接口、`/gateway/v1/` Agent 服务接口路由到正确目标；后端通过 `APP_ROOT_PATH` 感知外部挂载前缀以生成 API 文档地址，前端生产构建配置资源/API 前缀，本地 `npm run dev` 仍走根路径。数据库使用既有 PostgreSQL，不额外启动 Redis。

**面试重点：** Docker Compose 负责进程编排、网络和部署生命周期，Nginx 负责公网入口、TLS、静态资源和路径反代，两者职责不同。将 Nginx 留给服务器统一管理可以避免每个项目重复占用一个入口代理；网关后端仍是被代理的公网业务 API，因此反代不等于禁止外部调用。

### 案例 11：OpenAPI/Swagger 可执行示例与实现契约一致

**问题背景：** 开发过程中出现过用户在 Swagger 中找不到创建模板接口、参数显示或提交值不符合 UUID/文件格式、页面显示错误不完整等问题。接口“后端存在”不等于调用者能正确发现和执行。

**处理方案：** 以 FastAPI 实际路由生成 OpenAPI 契约，确认公开服务接口使用项目 API Key、控制台管理接口使用登录态/管理员权限；为请求字段补充类型、约束、描述和可运行示例。文件转写则定义 multipart 字段；实时音频明确为 WS JSON 控制消息加二进制 PCM，而不是把流式接口伪装成 HTTP 表单。

**面试重点：** API 文档是交付接口的一部分。需要从用户实际执行的 curl/Swagger 请求验证契约、鉴权方式和返回值，而不只是检查 schema 能否生成。

### 案例 12：管理员批量配置与上游 API 身份去重

**问题背景：** 管理员录入供应商连接时，希望一次粘贴多行 Key；每行应创建一条独立上游凭据，但相同 URL/Resource ID 与 Key 的组合不能因填写了不同组名而重复创建。ASR 的管理表单也需要沿用 LLM 已经验证过的分组与多 Key 操作方式。

**难点与方案：** 前端按换行拆分 Key 只是易用性处理，不能作为数据约束；调用方并发提交或通过 API 绕过页面时仍可产生重复记录。因此后端逐条规范化和校验，按连接身份加密 Key，同时以 HMAC 指纹和数据库唯一约束防止跨组重复；更新时排除当前记录再比较。ASR 连接的身份还要包含 Resource ID 及文件/实时端点，因为同一 Key 配置到不同资源或模式端点时不一定是同一个连接。

**面试重点：** 前端校验改善操作体验，真正的一致性必须在服务端与数据库约束中完成；展示分组（供应商、连接名、前缀）是管理视图，不能改变凭据唯一性的业务定义。秘密字段只在服务端加密保存，不进入普通用户可见的供应商目录。

### 案例 13：ASR 空结束帧触发上游 gzip 解码错误

**问题现象：** 实时会话握手和音频上传都已成功，调用方发出 `end` 后火山返回 `45000000`，错误为 `unable to ungzip payload: EOF`。这与没有上游权限或 URL 错误不同：Trace 显示上游 WebSocket 已返回 `101`，失败发生在结束帧解码阶段。

**根因：** 网关的空结束音频帧载荷长度为 0，但帧头仍声明 gzip 压缩。上游据压缩标记尝试解压空载荷，因此报告 gzip 数据提前结束。

**修复和验证：** 编码器现在只在压缩后确实有音频载荷时设置 gzip 标记；空 final 帧保留结束标志和负序号，但声明未压缩的空载荷。新增协议回归测试校验帧头、负序号和零载荷长度。修复后 ASR 协议与流式定向测试 22 项通过，Ruff 检查通过；该 Trace 对应的运行环境仍需加载新版本后再做真实上游复测。

**面试重点：** 从错误码和阶段定位，而不是看到“ASR失败”就先改 Key 或 URL；二进制协议的 header 与 payload 必须保持一致，并用精确的编码测试覆盖空包边界。

### 案例 14：上游空闲超时与静音续流的成本取舍

**问题现象：** 一条会话成功连接并收到 partial，之后上游报 `45000081`，内容为等待下一个数据包超时、会话已结束。另一次会话则在客户端发送 `end` 后立即暴露结束帧编码问题。两类失败都发生在 ASR，但原因和处理方式不同。

**排查结论：** `45000081` 表示上游等待音频包超过约 8 秒后结束会话；日志没有音频帧明细，无法仅凭 Trace 确定是客户端停发、采集链路断流还是传输中断。它不是一个可无限暂停后自动恢复的状态，超时关闭后应视为原 ASR 会话结束。

**方案取舍：** 在静音期间持续发送 PCM 零值帧可能让上游继续运行，也可能将这些音频时长计入上游费用；没有供应商账单或明确计费规则前，不能承诺静音帧免费。应由业务按静音时长策略决定何时结束当前 ASR 会话、何时在用户恢复说话时重连，并处理新旧会话的 utterance 边界。当前项目确认了超时行为及成本风险，尚未实现自动暂停/重连策略，也未实测供应商对此场景的具体计费。

**面试重点：** 说明传输连接保活和模型音频计费不是同一件事。不能为了避免超时就无条件发送静音，也不能把上游超时描述成“暂停后自动续传”；需要把产品交互、计费规则和会话状态机一起决策。

### 案例 15：利用握手状态和 Trace 阶段区分代理路径与 Provider 故障

**排查方法：** WebSocket 建连前收到 HTTP `404`，说明公开路径没有命中目标 WS 路由，需要检查 Nginx location、前缀改写和 WebSocket 转发；握手 `101` 只证明已经连到应用/上游，不能证明音频帧协议正确。网关日志中的 `asr_stream_upstream_connected`、`asr_stream_input_ended` 和 `asr_stream_failed` 可进一步区分连接、客户端结束输入和 Provider 解码/超时阶段。

**面试重点：** 将一次请求按公网入口、网关 WebSocket、Provider 握手、音频帧、最终事件逐层定位。Trace ID 用来串联这些阶段；每一层状态码的含义不同，不要把 404、上游 101、45000000 和 45000081 当成同一种“网络问题”。

## 三、面试复习顺序

建议优先准备案例 1、3、4、5、6、13 和 14：它们覆盖多租户权限、安全凭据、并发额度、实时双向协议、Provider 边界、事件幂等、协议层排错和计费取舍。每个案例按“业务影响 → 真实症状 → 根因 → 方案和取舍 → 验证 → 仍有限制”讲述。面试官追问时，准备说明具体数据边界、失败/取消路径和为什么不采用更简单但不可靠的方案。
